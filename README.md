# kg-skills：通用文档知识治理与开放服务技能包

本技能包把多模态文档治理为可追溯的证据、知识、方法规则和案例资产，再以不可变知识包向上层应用提供检索、问答、推荐、只读校验、反馈回流和变更影响服务。

它是独立通用知识平台的能力验证与执行规范，不包含上层应用的业务对象 CRUD、任务流转、审批、正式成果编排或自动写回。行业、地区、机构、词表和场景规则只能写入当前工作区配置或`integrations/`适配包，不能固化到核心 Skill。

## 1. 环境准备（一次性，约 10 分钟）

### 1.1 确认 Python

打开终端（Windows：开始菜单搜 `PowerShell` 回车；macOS/Linux：打开 Terminal），输入：

```bash
python --version
```

**你应该看到**：`Python 3.10.x` 或更高版本号。

- 版本低于 3.10，或提示“不是内部或外部命令 / command not found”：先到 python.org 安装最新版 Python，安装时勾选 “Add Python to PATH”，然后关掉终端重开一次再试。

### 1.2 进入技能包目录

后文所有命令都默认在技能包根目录执行（即本 README 所在目录）。在终端输入（把路径换成你机器上的实际位置）：

```bash
cd <你的项目路径>/kg-skills
```

**检查点**：执行 `ls`（Windows 用 `dir`）能看到 `kg-pipeline`、`kg-normalize`、`tests` 等目录。

### 1.3 安装依赖

```bash
python -m pip install -r requirements.txt
```

**你应该看到**：一串下载安装信息，最后没有红色 `ERROR`。出现网络超时可加国内镜像：

```bash
python -m pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
```

可选安装离线 OCR（处理扫描件/图片才需要，不装也能跑，图片文字会走大模型视觉转写路径）：

```bash
python -m pip install rapidocr-onnxruntime
```

嵌入模型已内置在`kg-package/scripts/_models/`，离线可用。PostgreSQL、NebulaGraph 及驱动只在启用外部数据库投影时才需要，第一次跑不用管。

### 1.4 跑自检（必做）

```bash
python tests/run_smoke.py
```

**你应该看到**：输出若干阶段信息，最后包含 `"passed": true`。这说明你的环境可以完整跑通“归一→接入→打标→生产→组包→检索→校验→回流→影响”的样例链路。

- 自检失败：先解决报错（通常是依赖没装全），**不要**带着失败的环境去处理真实资料。

自检通过后，环境就绪，本章不用再回来。

## 2. 基本概念（5 个名词 + 2 种用法）

| 名词 | 一句话解释 |
|---|---|
| **Skill** | 一份“操作规程”（`SKILL.md`）+ 配套脚本，由支持 Skills 的 Agent（Codex、Claude Code、WorkBuddy 等）阅读并执行；共 20 个，各管一段流程 |
| **工作区** | 一次治理批次的专属目录（如`治理工作区-20260701-0900/`），所有中间产物、资产和日志都在里面；不同批次不共用 |
| **人工关卡** | 流程中 4 个必须由人确认的点（词表、服务单元、治理配置、发布审核）。Agent 可以预填建议，但不能替你确认 |
| **知识包** | 治理完成后冻结的不可变发布单元，带逐文件哈希和版本号；对外服务只读知识包，不读工作区草稿 |
| **受限试跑** | 存在未确认项（来源、权限、时效、冲突）时允许的发布级别；所有待确认项关闭后才能“生产发布” |

**两种使用方式**：

| 方式 | 适用情况 | 操作特点 |
|---|---|---|
| 路线 A：`kg-pipeline`总控 | 首次治理、完整试跑、增量更新、断点续跑 | 给 Agent 一条完整指令，它自动判断阶段并调度，在人工关卡暂停等你确认 |
| 路线 B：分步调用 | 调试单个阶段、精细控制产物、替换某一步实现 | 按顺序逐个调用 Skill，逐阶段检查输入、输出和验收门槛 |

所谓“一键”是指只需触发一次`kg-pipeline`，不代表绕过人工审核——四个关卡必须保留。

**怎么“调用一个 Skill”**：在支持 Skills 的 Agent 对话框里直接说“使用 kg-pipeline …”或“使用 kg-normalize …”即可。不支持 Skills 机制的 Agent，把目标 Skill 的`SKILL.md`全文作为系统指令贴进去，再按其中命令执行脚本。

项目中维护五套一致镜像，任选其一使用（内容完全相同）：

| 目录 | 用途 |
|---|---|
| `.agents/skills` | 工作副本和统一来源 |
| `.claude/skills` | Claude Code 技能目录 |
| `.codebuddy/skills` | CodeBuddy 技能目录 |
| `.workbuddy/skills` | WorkBuddy 技能目录 |
| `kg-skills` | 独立 Git 发布仓库 |

## 3. 准备输入（三样东西）

开始前需要准备：① 源文档目录，② 来源映射文件，③ 治理工作区配置。照抄下面模板改成你的内容即可。

### 3.1 源文档目录

支持 DOCX、PDF、XLSX、PPTX、HTML、图片、扫描件、`.md`和`.markdown`。按来源分子目录摆放（允许继续嵌套）：

```text
原始资料/
├── source-map.json          ← 3.2 节的来源映射文件
├── 根目录说明.md
├── 正式资料/
│   ├── 制度文件.docx
│   └── 会议材料/会议纪要.pdf
├── 调研材料/
│   └── 访谈记录.markdown
└── 历史案例/
    ├── 成果清单.xlsx
    └── 流程图.png
```

**摆放检查点**：

- [ ] 老格式`.doc`/`.xls`已转存为`.docx`/`.xlsx`；
- [ ] 流程图、扫描件放原图（PNG/JPG/PDF），**不要**只放人工转好的 Markdown——原件是证据；
- [ ] 已有 Markdown 可以直接放入，系统同样会保存原件、登记多模态清单，不会跳过治理；
- [ ] 首次试跑建议 12–20 份代表性文件，不要一次投几千份。

### 3.2 来源映射 `source-map.json`

在源根目录创建`source-map.json`，为每个来源目录固定来源码、地区和机构（未配置的目录会自动分配来源码）：

```json
{
  ".": {
    "code": "ROOT",
    "region": "未知",
    "organization": "资料提供方"
  },
  "正式资料": {
    "code": "FORMAL",
    "region": "示例地区A",
    "organization": "示例机构"
  },
  "历史案例": {
    "code": "CASESRC",
    "region": "示例地区B",
    "organization": "历史项目组"
  }
}
```

来源码用稳定的 ASCII 大写字母和数字。**编号一旦进入治理，不要通过修改来源码重新编号。**

### 3.3 治理工作区与 `治理参数.json`

每个批次新建一个带时间戳的独立工作区目录，例如`治理工作区-20260701-0900/`（目录规范见`kg-pipeline/references/data-model.md`，路线 A 会自动创建）。工作区内至少准备`治理参数.json`：

```json
{
  "domain_code": "DOM",
  "projection_prefix": "kg_dom",
  "knowledge_version": "v0.1",
  "publication_level": "受限试跑",
  "tagging": {
    "source_levels": {
      "FORMAL": "正式资料",
      "CASESRC": "历史案例资料"
    },
    "regions": ["示例地区A", "示例地区B"],
    "domains": [
      {
        "name": "示例业务域",
        "code": "D01",
        "keywords": ["关键词A", "关键词B"],
        "labels": [
          {
            "name": "示例主题",
            "keywords": ["主题同义词A", "主题同义词B"]
          }
        ]
      }
    ],
    "genres": [
      {
        "name": "规范文件",
        "patterns": ["规范", "制度"]
      }
    ]
  },
  "applicability_versions": [
    {
      "code": "MAIN",
      "name": "示例适用版",
      "source_codes": ["FORMAL"]
    }
  ],
  "common_knowledge": []
}
```

> 注意：`tagging.domains`必须先形成候选并经人工确认（第 5 章第 2 步的关卡）。上面的示例值只能作为结构参考，**不能直接当成真实领域词表**。

## 4. 路线 A：一键全流程（推荐新手）

### 4.1 发出总控指令

在支持 Skills 的 Agent 中，把下面提示词改好路径后整段发送：

```text
请使用 kg-pipeline 对以下资料执行完整知识治理：

源文档目录：D:/path/to/原始资料
治理工作区：D:/path/to/治理工作区-20260701-0900
知识域名称：<知识域名称>
目标发布级别：受限试跑
人工确认方式：每个确认关卡暂停，输出待确认清单后等我确认

要求：
1. 从 kg-normalize 开始，按阶段检查并调度全部必要 Skill；
2. 保留原件、视觉快照、结构化对象和 Markdown 文本副本；
3. 任一事实必须能回溯到原始文件和精确定位器；
4. 有效依据、上位约束、现状事实、历史材料、实践经验、方法规范和模型建议分区治理；
5. 未关闭的待确认项只能进入受限试跑，不得宣称生产发布完成；
6. 每完成一个阶段更新操作日志，并报告当前产物、阻断项和下一步。
```

发出后 Agent 会自动创建工作区、依序执行，正常调度顺序为：

```text
kg-normalize → kg-intake → kg-tagging → kg-scenario-map → kg-govern-config
→ kg-evidence-govern → kg-method-rule / kg-case-asset / kg-produce
→ kg-coordinate → kg-package → kg-serve / kg-open-service / kg-service-harness
→ kg-feedback / kg-impact
```

### 4.2 中途你要做的四件事（人工关卡）

Agent 会在四个点暂停并给你“待确认清单”，你逐项回复确认/修改/否决即可：

| 关卡 | Agent 给你什么 | 你要做什么 |
|---|---|---|
| ① 词表确认 | 业务域、主题标签、同义词、知识角色候选 | 核对名称是否是你的业务叫法，同义词是否归并正确 |
| ② 服务单元确认 | 候选知识服务单元清单及拆分理由 | 逐项采纳/合并/否决/改名；地区、时间、外部任务阶段不能当单元 |
| ③ 治理配置确认 | 每个单元的资产组合建议、扩展资产建议和服务策略 | 确认问答对、知识块、Wiki、图谱的选择；确认证据、案例、方法规则、流程结构等扩展资产、权限和缺口降级策略 |
| ④ 发布审核 | 包清单、审核清单、质量报告 | 决定“受限试跑发布”“生产发布”或“退回治理”；有待确认项只能选受限试跑 |

### 4.3 批处理预填（材料多时用）

```text
使用 kg-pipeline 批处理本批资料。词表、服务单元、资产组合和发布审核按建议值预填，统一生成待确认清单；未确认项保持待确认，只允许受限试跑发布。
```

预填≠确认：批处理跑完仍需回头逐项确认，才能升级发布级别。

### 4.4 断点续跑（中断后接着跑）

```text
使用 kg-pipeline 继续治理 D:/path/to/治理工作区-20260701-0900。
先按阶段产物和完整性判断断点，从第一个未完成或校验失败的阶段继续；不要重建已确认且未受影响的资产。
```

总控按以下关键产物识别进度：

| 关键产物 | 表示阶段 |
|---|---|
| `00-原始MD/转换清单.md`和`00-多模态清单/多模态清单.jsonl` | 已执行格式归一 |
| `00-识别质检/归一验收报告.json`为通过 | 允许进入接入 |
| `00-文档台账/台账.md` | 已完成接入 |
| `20-打标结果/文档级打标.md` | 已完成打标候选 |
| `30-业务图与场景/单元场景目录.md`且状态已确认 | 已确定知识服务单元 |
| `40-治理配置/治理任务清单.md` | 已形成生产任务 |
| `50-知识资产/_协同/协同校验报告.md` | 已完成组包前校验 |
| `60-知识包/发布记录.md`和版本快照 | 已发布知识包 |
| `80-知识库导出/导出报告.md` | 已生成服务投影 |

文件存在不等于阶段完成。总控还必须检查状态、数量对账、人工确认和校验结论。

## 5. 路线 B：分步执行全流程（12 步）

以下命令均从技能包根目录执行；`<工作区>`替换为你的工作区路径（Windows 路径含空格时整体加双引号）。**仅运行脚本不能替代对应 Skill 中的语义分析和人工审核**——每步先用“触发方式”让 Agent 干活，脚本是其中的确定性部分。

每步统一四段：**做什么 → 怎么做 → 你应该看到 → 检查点**。

### 5.0 执行顺序、产物和使用方式总览

`kg-pipeline`是路线 A 的总控入口；如果走路线 B，就按下表从第 0 步开始逐个 Skill 执行。表里的“核心产物”都是后续步骤的正式输入，不是临时文件。

| 顺序 | 执行 Skill | 执行后具体做什么 | 生成什么产物 | 产物做什么用 | 如何使用 |
|---|---|---|---|---|---|
| 总控 | `kg-pipeline` | 创建/识别工作区，判断断点，按顺序调度各 Skill，并记录操作日志 | 工作区目录、`治理参数.json`、`90-审计日志/操作日志.md` | 作为一次治理批次的总目录和审计入口 | 新项目用路线 A 一键启动；中断后让它按关键产物判断断点续跑 |
| 0 | `kg-normalize` | 归一 DOCX/PDF/XLSX/PPTX/HTML/图片/扫描件/已有 Markdown；保留原件、抽文本、建视觉快照和结构化对象；完成 OCR 或视觉复核 | `00-原始资料/`、`00-原始MD/`、`00-视觉快照/`、`00-结构化对象/`、`00-多模态清单/多模态清单.jsonl`、`00-识别质检/` | 保证任何后续知识都能回到原件；避免表格、流程图、图片细节在 Markdown 化时丢失 | 先看`归一验收报告`；有`待视觉转写/已OCR-待视觉复核/结构识别失败`就补视觉复核，不得进入下一步 |
| 1 | `kg-intake` | 读取归一结果，建立文档编号、版本、哈希、权限、时效、知识角色和段落/页面/表格/图区定位器 | `10-解析文档/{来源码}/{编号}.md`、`00-文档台账/台账.md`、`00-文档台账/文档版本.jsonl`、`00-文档台账/定位器映射.jsonl` | 形成统一文档底账和可引用锚点，是打标、证据、溯源的基础 | 后续所有引用都用`文档编号#pNNN`等定位器；人工修订解析文档后重建台账 |
| 2 | `kg-tagging` | 先生成词表候选并等人工确认，再给文档和段落打业务主题、内容单元、知识角色、地区、对象、时间、权限等标签 | `20-打标结果/词表与标签体系.md`、`文档级打标.md`、`段落级打标/`、`待人工确认清单.md` | 决定文档属于哪些知识主题、哪些内容可进入证据/方法/案例/服务单元 | 先确认词表和同义词；用文档级标签做服务单元拆分，用段落级标签做深治理和证据候选 |
| 3 | `kg-scenario-map` | 建立知识覆盖图，拆分可独立治理、发布、授权的知识服务单元，叠加地区/对象/时间版本，盘点覆盖缺口 | `30-业务图与场景/人工边界配置.md`、`候选单元场景清单.md`、`单元场景目录.md`、`全局业务图.md`、`地区版本映射.md`、`场景覆盖盘点.md` | 确定后续治理任务的颗粒度和服务路由目录 | 人工采纳/合并/否决/改名后，只有`状态=已确认`的服务单元才能进入治理配置 |
| 4 | `kg-govern-config` | 针对每个服务单元和适用版本选择资产组合；问答对、知识块默认必选，Wiki 和图谱按需独立选择；配置证据、案例、方法规则、流程结构、服务策略和缺口降级 | `40-治理配置/治理方式配置.md`、`治理任务清单.md`、`变更记录.md` | 把“要治理什么资产、按什么顺序生产、谁来校验、如何服务”固化为任务 | 逐单元确认资产选择；`治理任务清单`是`kg-evidence-govern`、`kg-method-rule`、`kg-case-asset`、`kg-produce`的执行依据 |
| 5 | `kg-evidence-govern` | 把解析文档、表格、图片和流程资料治理为可定位证据卡，区分有效依据、上位约束、现状事实、历史材料、实践经验、方法规范、模型建议，并登记冲突和缺口 | `50-知识资产/_证据/证据卡.jsonl`、`证据索引.md`、`冲突与缺口.md` | 作为问答、推荐、校验、案例复用和发布审核的可信依据层 | 检索和生成时只使用有权限、时效和适用范围匹配的证据；冲突/缺口不能被模型补平 |

### 5.1 工作区产物字典：每个目录和文件怎么理解

这一节按工作区目录说明每个关键产物记录什么、由谁生成、给谁使用。实际执行时遇到某个文件不知道怎么用，优先查这里。

#### 根目录

| 产物 | 记录什么 | 谁生成/维护 | 给谁用 | 怎么检查/使用 |
|---|---|---|---|---|
| `README-数据规范.md` | 本工作区采用的数据目录、编码、引用和发布规则 | `kg-pipeline`创建工作区时从`kg-pipeline/references/data-model.md`复制 | 所有执行人员和 Agent | 工作区交接时先读它；如果 README 和本文件冲突，以当前工作区内的配置和人工确认记录为准 |
| `治理参数.json` | 本批治理的业务域码、投影前缀、知识版本、发布级别、标签词表、来源层级、适用版本、共性知识配置 | 人工准备，`kg-pipeline/kg-tagging/kg-scenario-map/kg-produce/kg-package`读取 | 全流程配置入口 | 不能写死行业或地区到 Skill；换场景主要改这里和`integrations/`适配包 |
| `_scripts/` | 本批临时脚本、一次性转换脚本或排障脚本 | 人工或 Agent 按需放置 | 当前批次临时处理 | 不作为核心 Skill 的一部分；可审计但不依赖它复现核心流程 |

| 产物 | 记录什么 | 谁生成/维护 | 给谁用 | 怎么检查/使用 |

### 第 0 步：多模态归一（kg-normalize）

**做什么**：把所有格式的原始文件转成“原件快照 + 视觉快照 + 结构化对象 + Markdown 文本副本”四种关联表达；图片和扫描件在这一步完成文字识别。

**怎么做**：

```text
使用 kg-normalize 归一 <源文档目录> 到 <工作区>，检查已有 Markdown、复杂表格、流程图和扫描件是否完整进入清单。
```

```bash
python kg-normalize/scripts/normalize.py <源文档目录> <工作区>
```

| 词表确认 | 业务域、主题、同义词、知识角色和置信度规则 | 可继续预填，不可视为正式打标结论 |
| 服务单元确认 | 采纳、合并、否决、改名、编码和适用版本 | 不得按未确认目录生产正式资产 |
| 治理配置确认 | 问答对、知识块、Wiki、图谱资产组合，扩展资产、权限、缺口和调整触发条件 | 仅可生成试跑任务 |
| 发布审核 | 来源、权限、时效、冲突、质量、回滚点和发布级别 | 只能受限试跑或退回治理 |

## 8. 常见阻断及处理

| 阻断 | 原因 | 处理 |
|---|---|---|
| `待视觉转写` | OCR 不可用或没有有效文字 | 用视觉能力逐图转写，修正文副本后登记复核 |
| `已OCR-待视觉复核` | 低置信、复杂结构或关键字段 | 核对数字、表格、流程、印章和版面结构 |
| 文档数量不一致 | 源文件、文本副本、多模态清单或台账漏件 | 停止接入，修复来源发现或文档 ID 对账 |
| 标签大量待确认 | 词表缺失、同义词不足或仅看标题 | 回到词表确认并抽读代表文档 |
| 服务单元边界重叠 | 把地区、时间或外部任务阶段当成服务单元 | 回到`kg-scenario-map`合并或改为适用维度 |
| 知识块缺锚点 | 内容无法回到原始文档 | 退回`kg-produce`补真实定位器或标记缺口 |
| 跨适用域知识冒充目标域事实 | 角色混用或缺适用分区计算 | 按请求上下文×适用范围重算分区并增加适配待确认条件 |
| 同版本内容变化 | 已冻结版本被修改 | 禁止覆盖，生成新知识版本 |
| 待确认项未关闭 | 不满足生产发布门槛 | 保持受限试跑或退回治理 |
| 依赖安装失败 | 网络或 Python 版本问题 | 换国内镜像源；确认 Python ≥ 3.10 |
| 脚本找不到文件 | 未在技能包根目录执行，或路径含空格未加引号 | `cd`到根目录；Windows 路径整体加双引号 |

## 10. 维护约定

`.agents/skills`是工作副本来源。任何 Skill、脚本、参考文件、集成配置、测试或本 README 发生变更后，必须同步维护`.claude/skills`、`.codebuddy/skills`、`.workbuddy/skills`和独立发布仓库`kg-skills`。

同步时保留`kg-skills/.git`，不要复制`__pycache__`。同步后必须执行：

1. 四个镜像与`.agents/skills`逐文件哈希比对。
2. 核心通用性审计。
3. Markdown 直通和配置驱动试跑。
4. 完整冒烟测试。
5. 20 个 Skill 的`quick_validate`结构校验。
