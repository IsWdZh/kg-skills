# kg-pipeline：知识治理总控

## 核心理念

> 原件和治理态是知识事实源；外部业务应用是自身业务事实源。先形成多模态来源、证据和知识服务单元，再按需生产知识、方法规则与案例，通过标准接口提供检索、推荐、校验、回流和影响通知。

对象链路：`原件/多模态表达 → 标签与证据 → 知识服务单元 → 知识/方法/案例资产 → 不可变发布包 → 开放服务 → 反馈/影响`

## 启动流程

1. **确认输入**：源文档目录（按来源分子文件夹，可用`source-map.json`配置来源码/地区/机构）、知识域名称、治理工作区位置（默认在项目根目录建 `治理工作区/`）。
2. **创建工作区**：按 [references/data-model.md](references/data-model.md) 建目录结构，并把该文件复制为 `<工作区>/README-数据规范.md`。在 `<工作区>/治理参数.json` 设置业务域码、投影前缀、标签词表和适用版本；这些值属于工作区配置，不得写死在 Skill 中。每次独立运行（演示/多批次）使用带时间戳的工作区名（如 `治理工作区-YYYYMMDD-HHMM/`）；`load_pg`/`load_nebula` 按 `projection_prefix + 时间戳` 生成独立投影名，也可分别由命令行或环境变量覆盖。
3. **判断当前阶段**（断点续跑的关键）：

| 检查（按序） | 存在且完整 → 已过该阶段 |
|---|---|
| `00-原始MD/转换清单.md` | kg-normalize（第 0 环节：统一转 md） |
| `00-多模态清单/多模态清单.jsonl` | kg-normalize（原件、视觉、结构化、文本关联） |
| `00-文档台账/台账.md` | kg-intake |
| `20-打标结果/文档级打标.md` | kg-tagging |
| `30-业务图与场景/单元场景目录.md`（状态=已确认） | kg-scenario-map |
| `40-治理配置/治理方式配置.md` | kg-govern-config |
| `50-知识资产/{场景}/{地区}/` 资产与任务清单对账 | kg-produce |
| `50-知识资产/_证据/证据卡.jsonl` | kg-evidence-govern |
| 方法/规则或案例治理任务存在时对应资产通过校验 | kg-method-rule / kg-case-asset |
| `50-知识资产/_协同/协同校验报告.md` | kg-coordinate |
| `60-知识包/发布记录.md` 含当前有效版本 | kg-package |
| 当前版本目录含`资产/`、逐文件 SHA-256 与包指纹 | kg-package 已冻结 |
| `80-知识库导出/导出报告.md` | 服务投影已生成 |
| `70-服务运行/调用协议.md` | kg-serve 就绪 |
| 集成配置契约与权限测试通过 | kg-open-service / kg-service-harness |

4. **调度执行**：从第一个未完成阶段开始，依序调用对应技能。每完成一个阶段，在 `90-审计日志/操作日志.md` 追加一行（时间/阶段/操作/对象/执行者）。

## 全程纪律（对所有子技能生效）

1. **溯源强制**：任何知识内容必须带 `编号#pNNN` 锚点；无来源不落盘。
2. **人工确认关卡**：词表、场景目录、治理配置、发布审核四处必须有显式确认动作。交互式=逐项问用户；批处理式=按建议值预填并汇总到待确认清单。批处理预填不等于业务审核，存在待确认项时只能受限试跑，不能宣称生产发布完成。
3. **不编造**：文档没写的内容不得出现在知识资产里；覆盖缺口走显式降级（见 kg-produce/kg-serve）。
4. **时间规范**：一律 `YYYY-MM-DD`，缺失写`未知`并在完整性标记。
5. **增量稳定**：新文档进入或治理方式变更时，只重做受影响的场景/地区版本，不重建全局（先做影响分析：新文档打标→命中哪些场景→仅对命中项生成重新治理任务）。
6. **发布不可变**：`50-知识资产/`允许继续编辑；`60-知识包/{场景}/{地区}/vX.Y/资产/`一经发布不得改写。任何修订必须生成新版本，并重新冻结、导出、验收。
7. **权限与时效贯穿**：来源网址、访问范围、责任人、时效状态从接入一路传递到资产、知识包、检索过滤和答案；未知值必须显式呈现。
8. **知识角色隔离**：有效依据、上位约束、现状事实、历史材料、实践经验、方法规范和模型建议不得混用。服务时按请求上下文×知识适用范围计算分区：适用命中/跨域参考；跨适用域知识只能进入参考分区，不得作为目标域确定性依据，不得填平缺口。
9. **双主数据禁止**：外部对象只以 ID、版本、只读快照和证据映射进入知识服务；任何 Skill 都不得写回业务状态或审批结论。
10. **服务闭环**：发布后按需调度 `kg-context-retrieve → kg-recommend/kg-verify`；确认反馈经`kg-feedback → kg-case-asset`回流；知识换版调度`kg-impact`。
11. **全量对账**：原始格式不得成为下游过滤条件。每个阶段开始前核对上游唯一文档 ID 集合，至少满足`源文件清点 = 00-原始MD = 多模态清单 = 文档台账 = 10-解析文档`；原始 Markdown 与转换生成的 Markdown 同等进入打标、证据、生产、协同和发布。

## 试跑验证基准

至少执行一套领域样本和两个不同类型的上层调用方：文档多表达与证据可定位、权限过滤、角色分区、推荐不越权、只读校验、成果回流、影响通知和跨应用调用全部通过。任何历史专项试跑都只能作为兼容回归，不能成为核心能力的默认词表、命名或数据结构。
